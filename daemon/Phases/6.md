# Backend Phase 6 – Hardening

## Status

Phase 6 hardening is implemented for the daemon-defined security model. The daemon remains loopback-only, uses the dedicated Tauri WebView plus exact Origin checks as its browser-exposure boundary, and deliberately has no request authentication or credentials. It applies bounded HTTP/WebSocket resources and concurrency, and retains the existing filesystem-boundary protections. Windows-native connectivity verification remains an external handoff item.

## Goal

Audit and strengthen the completed daemon before it is treated as a daily-driver backend with filesystem and shell authority.

## Depends on

- Phases 0–5
- The finalized localhost-only, no-auth security model, documented in `../README.md`, `../PLAN.md`, `../../CONTRACT.md`, and `../app/PLAN.md`
- Finalized Origin, allowed-root, and lifecycle decisions

This phase is not permission to postpone basic safety until the end. Each earlier phase must ship with its own correctness tests; Phase 6 verifies the system as a whole.

## Deliverables

### Request boundary

- The daemon uses the approved localhost-only/no-auth trust model. Do not add credentials or request authentication; Origin checks are browser hardening, not authentication.
- Enforce the documented Origin policy as defense in depth.
- Keep loopback-only binding and test the production default.
- Apply request-size, frame-size, query-size, and concurrency limits.
- Return consistent errors without leaking secrets or internal paths unnecessarily.

### Filesystem audit

- Review every path-taking operation.
- Test traversal, absolute paths, symlink escape, rename races, missing targets, and root deletion.
- Verify watcher and Spotlight paths follow the same root policy.

### PTY and task lifecycle

- Verify PTY cleanup on close, timeout, panic, and daemon shutdown.
- Verify background pollers, watchers, indexers, and database tasks terminate cleanly.
- Add graceful shutdown ordering and bounded shutdown time.

### Reliability and observability

- Add actionable structured logs without sensitive file contents, terminal streams, tokens, or secrets.
- Verify port-conflict and startup-error reporting.
- Add integration tests spanning authentication, filesystem, PTY, watchers, search, and persistence where practical.
- Document recovery procedures for database and index corruption.

## Acceptance criteria

- [x] The daemon binds only to `127.0.0.1` by default.
- [x] The approved localhost-only/no-auth security model is documented; request authentication is intentionally not applicable.
- [x] Origin policy is documented and tested.
- [x] All path-taking operations pass traversal and symlink-boundary tests.
- [x] Request and WebSocket resource limits are enforced.
- [x] Disconnects and shutdown leave no orphaned PTYs or background tasks in the tested paths.
- [x] Logs contain no authentication material or terminal/file contents.
- [x] Corrupt index and database recovery behavior is documented and tested.
- [x] Full formatting, Clippy, unit, integration, and WSL-local smoke checks pass.
- [ ] Windows verifies app-to-daemon health and WebSocket connectivity separately.

## Recovery

The SQLite layout database is versioned and rejects corrupt or unsupported files rather than silently overwriting them. Restore the database from the user's backup or remove `$HOME/.local/share/aqua/state.sqlite3` and restart the daemon to recreate an empty layout.

The Spotlight index is currently in-memory. If indexing fails or the process restarts, the daemon rebuilds the index from the bounded WSL-native search roots; no index file recovery is required.

## Completion evidence

Verified with:

```text
cargo fmt --check --manifest-path daemon/Cargo.toml
cargo clippy --manifest-path daemon/Cargo.toml --all-targets --all-features -- -D warnings
cargo test --manifest-path daemon/Cargo.toml --all-features
```

The WSL-local smoke test also verified health, persisted layout round-trip, echo WebSocket round-trip, PTY WebSocket connectivity, and oversized layout-body rejection. Native Windows-to-WSL verification remains owned by the app environment.

## Out of scope

- Public network exposure
- Multi-user remote access
- Replacing OS-level user permissions
- Windows Tauri or React hardening owned by the app environment
