# Backend Phase 5 – Persistence

## Goal

Persist and restore Aqua window and Space layout through SQLite.

## Depends on

- Phase 0 server foundation
- Layout shapes in `../../CONTRACT.md`
- A documented database location and migration policy

## Deliverables

- SQLite database initialization
- Versioned schema migrations
- Tables required for windows and Spaces
- `GET /api/state/layout`
- `PUT /api/state/layout`
- Transactional replacement or update of a complete `LayoutState`
- Safe storage and retrieval of app-specific JSON state
- Predictable first-run behavior when no layout exists
- Graceful handling of database corruption, lock contention, and incompatible schema versions

Recents and preferences may be included only if their API and ownership are documented. Do not create unused tables merely because they appear in the architecture sketch.

## Behavior

- Match `LayoutState`, `WindowState`, and `SpaceState` in `CONTRACT.md`.
- Validate duplicate IDs, invalid dimensions, unknown app identifiers, and references to missing Spaces according to a documented policy.
- Perform writes atomically so a crash cannot leave a partially updated layout.
- Keep layout-write debouncing in the frontend as planned; the backend still must tolerate repeated valid requests.

## Acceptance criteria

- [ ] A fresh database returns the documented empty or default layout.
- [ ] A valid PUT round-trips through GET without shape drift.
- [ ] Writes are transactional.
- [ ] Invalid layouts return structured errors without altering stored state.
- [ ] App-state JSON round-trips without semantic changes.
- [ ] Migrations are repeatable and tested from every supported schema version.
- [ ] Database files are written to the documented WSL-native data location.
- [ ] Formatting, Clippy, and all tests pass.

## Out of scope

- Frontend debounce implementation
- Cloud synchronization
- Multi-user state
- Arbitrary frontend-controlled SQL
