# Backend Phase 8 – Wallpaper

## Status

Implemented. Custom wallpaper uploads are stored daemon-side with generated thumbnails, tracked in SQLite (schema v2), and served through contract-shaped REST endpoints. Built-in wallpaper IDs remain frontend-owned; deleting the active custom wallpaper resets the selection to the built-in default. Windows-native verification remains an external handoff item.

## Design

- Storage lives under `~/.local/share/aqua/wallpapers/`, derived from the same root as the state database.
- Uploads are validated by decoding with the `image` crate before anything is written; PNG, JPEG, and WebP are accepted, capped at a 16 MiB body for this route only (the global 2 MiB limit still applies everywhere else).
- Thumbnails are fixed-width (480 px) PNGs generated at upload time; no runtime resizing cost later.
- Asset filenames are server-generated UUIDs, so client input never touches the filesystem path.
- Schema v2 adds `prefs` (key/value) and `wallpapers` tables; existing v1 databases migrate in place. The current selection reuses `prefs` under `wallpaper.current`.

## Endpoints

| Path | Behavior |
|---|---|
| `GET /api/wallpaper` | `{ current, custom: [{ id, label, addedAt }] }`; `current` defaults to `"aqua"` |
| `PUT /api/wallpaper` | `{ id }` – accepts built-in or custom IDs; stored in prefs |
| `POST /api/wallpaper/upload?label=` | Raw image bytes; returns `201` with the created wallpaper |
| `DELETE /api/wallpaper/:id` | Removes daemon-owned assets + row; unknown/built-in IDs fail; active selection falls back to `"aqua"` |
| `GET /api/wallpaper/asset/:id` | Full-resolution bytes with correct content type; 404 when absent |
| `GET /api/wallpaper/asset/:id/thumb` | Thumbnail bytes |
