# Backend Phase 7 – Elevation

## Status

Implemented. `POST /api/system/elevate` validates the sudo password through `sudo -S -v` (stdin only), caches a five-minute in-memory expiry, and gates `elevated: true` filesystem operations behind that cache. Elevated retries are executed by a separate single-shot helper binary (`aqua-daemon-helper`) invoked with `sudo -n`, which re-derives the `openat2` root boundary and re-runs every shared path-safety check before performing exactly one operation. Windows-native verification remains an external handoff item.

## Design

Follows the approved privilege-boundary design in the root `ELEVATION_RECOMMENDATION.md`:

- The password exists only transiently inside the `/api/system/elevate` handler. It is never stored, logged, or passed to the helper.
- The daemon never performs elevated work in-process. It hands one serialized operation to `sudo -n aqua-daemon-helper` and parses the structured result.
- The helper is a standalone binary with no Tokio runtime, no axum/tantivy/sysinfo dependency surface at execution time, and no persistent state. It reads one JSON request on stdin, re-validates everything fresh from its own process, writes one JSON result to stdout, and exits.
- Path-safety logic lives in `src/fs/safety.rs` and is shared by both the unprivileged daemon and the root helper. There are deliberately not two implementations.

## Deliverables

- `system::elevate` endpoint and five-minute in-memory expiry cache
- `elevated` field accepted on every `FsOp` variant; unknown-state requests without a valid cache return `needsElevation: true`
- `aqua-daemon-helper` binary performing single privileged operations with fresh `openat2` validation
- Shared path-safety module used by both processes
