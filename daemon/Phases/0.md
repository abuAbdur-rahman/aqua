# Backend Phase 0 – Daemon foundation

## Status

Implemented and verified inside WSL. The daemon binds to `127.0.0.1:61234`; Windows-to-WSL reachability remains pending until it is tested from the Windows-native app environment.

## Scope

Create the Rust daemon under `daemon/` and provide:

- a runnable Axum/Tokio server;
- `GET /api/health`;
- a WebSocket echo endpoint at `/ws/echo`;
- loopback-only binding on `127.0.0.1:61234`;
- structured startup and connection logging;
- tests for the health response and echo behavior;
- a documented local smoke test.

The daemon must not implement real filesystem operations, shell sessions, authentication, or persistence in this phase. Do not add speculative endpoints.

## Required contract

### Health

Request:

```http
GET /api/health
```

Expected successful response:

```json
{
  "status": "ok",
  "version": "0.1.0"
}
```

Requirements:

- `200 OK`;
- `Content-Type: application/json`;
- exact camelCase-compatible field names from `CONTRACT.md`;
- version sourced from one maintained project value, not duplicated across handlers and tests.

If the implementation chooses a different version, update the contract and explain the versioning choice before proceeding.

### WebSocket echo

Request:

```text
WS /ws/echo
```

For each supported incoming text or binary frame, return an equivalent outgoing frame without changing its payload. Preserve text as text and binary as binary.

Define and test behavior for:

- normal text frames;
- binary frames;
- ping/pong handling according to the selected Axum/WebSocket behavior;
- client close;
- malformed or unsupported frames, if the chosen implementation can receive them.

The echo route is a Phase 0 connectivity probe, not the eventual multiplexed application protocol.

## Binding and startup

- Bind exactly to `127.0.0.1:61234` by default.
- Port `61234` is Aqua's fixed daemon port. Define it once in code and derive the socket address from that constant.
- Do not bind to `0.0.0.0`.
- If configuration is introduced, keep the safe loopback address as the default and test that default.
- Log the listening address once at startup.
- Support graceful shutdown where practical, with Ctrl-C handling and a shutdown log.
- Do not spawn a second server inside tests on the fixed production port. Use an ephemeral test port for integration tests.

## Suggested layout

```text
daemon/
  Cargo.toml
  src/
    main.rs
    lib.rs
  tests/
    phase_0.rs
```

This is guidance, not a reason to create empty modules. Keep the layout proportional to the implementation.

## Acceptance criteria

Phase 0 is complete only when all of the following are true:

- [x] `daemon/` is a valid Rust crate.
- [x] `cargo fmt --check` passes.
- [x] `cargo clippy --all-targets --all-features -- -D warnings` passes.
- [x] `cargo test --all-features` passes.
- [x] A test verifies the health status and version JSON.
- [x] Tests verify text and binary echo payload preservation.
- [x] The default server binds to `127.0.0.1:61234`.
- [x] No route binds externally or exposes filesystem/PTY functionality.
- [x] A local smoke test confirms `curl http://127.0.0.1:61234/api/health` works while the daemon is running.
- [x] The README or backend documentation records that Windows-to-WSL reachability remains a separate verification step.

## Verification commands

From the repository root, use `--manifest-path daemon/Cargo.toml` with these commands.

```bash
cargo fmt --check --manifest-path daemon/Cargo.toml
cargo clippy --manifest-path daemon/Cargo.toml --all-targets --all-features -- -D warnings
cargo test --manifest-path daemon/Cargo.toml --all-features
cargo run --manifest-path daemon/Cargo.toml
```

In another shell while the server is running:

```bash
curl --fail --silent --show-error http://127.0.0.1:61234/api/health
```

Expected output should contain `"status":"ok"` and the documented version.

Windows verification is performed later from the Windows-native app environment using the equivalent `localhost:61234` request. Do not claim that check passed based on WSL-local output.

## Out of scope

Do not implement in Phase 0:

- filesystem listing or mutation;
- path validation;
- PTY allocation or shell execution;
- system statistics;
- Spotlight indexing;
- SQLite persistence;
- frontend or Tauri code;
- production authentication unless the security decision is made first.
